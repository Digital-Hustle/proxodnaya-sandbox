# ADR-039. Данные в масштабе: страницы, фильтры на сервере, превью вместо полных списков

Статус: принято. Контекст: песочница работает на моках (16 человек, 3 зоны), но реальный объект — сотни людей, десятки зон и КПП, десятки тысяч проходов в месяц. Интерфейс должен переехать на настоящий API без переделки экранов.

## Решение

1. **Ни один список не загружается целиком.** Люди, Журнал, Смены читают данные страницами через `api.queryWorkers`, `api.queryAttempts`, `api.queryShiftRows` (`src/shared/api/mock/server.ts`). Ответ всегда одинаковый: `{ items, nextCursor, total }`, лимит страницы ≤ 100 (`PAGE_MAX`).
2. **Подгрузка по мере прокрутки.** Хук `usePaged` + подвал `LoadMore` (IntersectionObserver за 400 px до края). Кнопка «Показать ещё» остаётся — для клавиатуры и скринридера. Внизу всегда «Показано N из M».
3. **Курсоры.** Журнал — курсор по ключу `ts~id` (новые проходы появляются сверху и не сдвигают страницы, дублей нет). Люди и Смены отсортированы по ФИО, там офсетный курсор; случайные дубли при вставке отсекаются по id на клиенте. Курсор непрозрачен для UI — сервер может поменять схему без правок экранов.
4. **Фильтры и поиск — на сервере.** Поиск с задержкой 250 мс (`useDebounced`), «ё» = «е». Фильтры лежат в адресе страницы; смена фильтра сбрасывает список на первую страницу, ответы устаревших запросов отбрасываются.
5. **Живые данные.** При новом проходе уже загруженное окно тихо перезапрашивается (без скелетона и без потери прокрутки). В продукте триггер — событие из SSE/WebSocket, а не изменение локальной базы.
6. **Превью вместо полных списков на обзоре.** «Сейчас на объекте» — 12 человек и ссылка «Все N на объекте →» в Люди с фильтром. Зон сколько угодно: до 6 — как есть, больше — 6 самых загруженных и «Все зоны · N». Лента событий — последние N, архив — в Журнале.
7. **Фильтры, которые растут вместе с объектом.** Люди: зона допуска и подрядчик. Журнал: проходная. Смены: поиск и «со сменой / без смены». Все списки зон и КПП строятся из данных, а не зашиты в вёрстку.
8. **Аналитика и помощник считают агрегаты, а не строки.** В песочнице агрегаты считаются в `mock/derived.ts`; в продукте это `GET /analytics?from=&to=` с уже посчитанными рядами по дням (материализованная витрина). Таблица в ответе помощника — не больше 30 строк, дальше «Ещё N строк».
9. **Выгрузка CSV** идёт отдельным запросом `api.exportAttempts` с теми же фильтрами — выгружается всё, а не только прокрученное. В продукте — фоновая задача и ссылка на файл.

## Пограничные случаи

| Случай | Поведение |
| --- | --- |
| Первая загрузка | Скелетон строк, а не пустое состояние |
| Пусто под фильтр | «Никого не нашли» + «Сбросить фильтры» |
| Пустая база | Приглашение завести первого сотрудника |
| Ошибка страницы | Уже загруженное остаётся, внизу «Не удалось загрузить» + «Повторить», автоподгрузка на паузе |
| Быстрый ввод в поиск | Задержка 250 мс, устаревшие ответы отбрасываются |
| Новый проход во время прокрутки | Тихое обновление окна, позиция сохраняется, дублей нет |
| Очень длинные ФИО/названия зон | Обрезаются многоточием, вёрстка не ломается |
| Зона с вместимостью 0 | Нет деления на ноль |
| Удалённый сотрудник в журнале | «Неизвестный пропуск», запись сохраняется |
| Выгрузка пустого фильтра | Подсказка вместо пустого файла |

## Как проверить

Настройки → Демо-режим → «Добавить 400 человек и 5 зон». Добавляются люди, 5 зон с КПП, смены на неделю и сегодняшние проходы. «Сбросить демо-данные» возвращает исходные 16 человек.

## Переход на настоящий API

Заменить тела функций `query*` на `fetch` с теми же аргументами и формой ответа. Экраны, `usePaged` и `LoadMore` не меняются. Индексы БД: `attempts(ts desc, id)`, `attempts(checkpoint_id, ts)`, `workers(full_name, id)`, `shifts(day, worker_id)`.
